# sound-app: Tauri Shell (PR 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Wrap the existing Vite + React frontend (`apps/sound-app`, from PR 1) in a Tauri v2 shell, proving the frontend↔Rust IPC bridge with a trivial `ping` command, with restrictive capabilities and no real recording functionality yet.

**Architecture:** Scaffold `src-tauri/` via the official Tauri v2 CLI's `init` command (safer than hand-authoring config against a schema that could be subtly wrong), then hand-edit the generated identifier/package names, add a `ping` command registered in the invoke handler, and add a matching frontend button. Verified three ways: `cargo test` (Rust side alone), a Vitest test with a mocked `invoke` (frontend wiring alone), and a manual `tauri dev` run on this machine's real Wayland display (the actual bridge, both sides for real).

**Tech Stack:** Tauri v2 (`tauri` crate 2.11.6, `@tauri-apps/cli` 2.11.5, `@tauri-apps/api` ^2), Rust (rustup stable 1.98.1, already installed), existing Vite + React 19 + Vitest stack from PR 1.

**Spec:** `docs/superpowers/specs/2026-09-20-sound-app-tauri-shell-design.md`

## Global Constraints

- App identifier: `com.soundrecorder.app` (not the CLI's generated placeholder `com.tauri.dev`).
- No shell or HTTP/network Tauri plugin gets added at all (restrictive by omission, per PRD §6.2). Note: the actual `tauri init` output for this CLI version (2.11.5) already omits `tauri-plugin-opener` by default — there is no plugin to prune, only to not add.
- App icons are deferred — keep the CLI-generated placeholder icon set as-is; do not source or generate branded icons in this PR.
- The existing `dev`/`build` Turbo tasks stay pure-Vite (unchanged) — the Tauri shell is invoked only via a new `"tauri": "tauri"` pass-through script, never folded into the default `dev` task.
- This machine has a real Wayland display (`DISPLAY=:0`, `WAYLAND_DISPLAY=wayland-0`) — the manual verification step in Task 4 opens an actual native window, not a headless stub.
- Custom `#[tauri::command]` functions are not gated by Tauri v2's capabilities/permissions system (that system governs plugin commands only) — `ping` needs no capability grant, only registration.

- [ ] **Step 3: Implement `ping` and register it**

Add the command function above the `run()` function, and register it in the builder chain. The full file should read:

```rust
#[tauri::command]
fn ping() -> String {
    "pong".to_string()
}

#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    tauri::Builder::default()
        .setup(|app| {
            if cfg!(debug_assertions) {
                app.handle().plugin(
                    tauri_plugin_log::Builder::default()
                        .level(log::LevelFilter::Info)
                        .build(),
                )?;
            }
            Ok(())
        })
        .invoke_handler(tauri::generate_handler![ping])
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn ping_returns_pong() {
        assert_eq!(ping(), "pong");
    }
}
```

(The only change from Task 1's generated `lib.rs` is adding the `ping` function, adding `.invoke_handler(tauri::generate_handler![ping])` to the builder chain, and the test module.)

```tsx
import { useState } from "react"

import { invoke } from "@tauri-apps/api/core"
import { Button } from "@workspace/ui/components/button"

import { ThemeProvider } from "./components/theme-provider"

export function App() {
  const [pingResult, setPingResult] = useState<string | null>(null)

  async function handlePing() {
    const result = await invoke<string>("ping")
    setPingResult(result)
  }

  return (
    <ThemeProvider>
      <div className="flex min-h-svh p-6">
        <div className="flex max-w-md min-w-0 flex-col gap-4 text-sm leading-loose">
          <div>
            <h1 className="font-medium">Project ready!</h1>
            <p>You may now add components and start building.</p>
            <p>We&apos;ve already added the button component for you.</p>
            <Button className="mt-2">Button</Button>
          </div>
          <div>
            <Button onClick={handlePing}>Ping backend</Button>
            {pingResult !== null && <p className="mt-2">{pingResult}</p>}
          </div>
          <div className="text-muted-foreground font-mono text-xs">
            (Press <kbd>d</kbd> to toggle dark mode)
          </div>
        </div>
      </div>
    </ThemeProvider>
  )
}
```

- **Task 1, Step 5** only added `@tauri-apps/api` as a dependency. The `"tauri": "tauri"` script it also added had no local `@tauri-apps/cli` devDependency to resolve, so `pnpm tauri dev` failed with "command not found" until Task 4 added `"@tauri-apps/cli": "^2.11"` as a devDependency — a genuine plan gap, not an implementation error.

No behavior change (confirmed: `Cargo.lock` was untouched by this).
