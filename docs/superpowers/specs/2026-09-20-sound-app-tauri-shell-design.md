# sound-app: Tauri Shell (PR 2 of 8)

Status: approved for planning
Scope: `apps/sound-app` only. Depends on PR 1 (Next.js → Vite migration, merged to master).

## Context

PR 1 converted `apps/sound-app` from Next.js to a Vite + React 19 + TypeScript SPA
(see `docs/superpowers/specs/2026-09-20-sound-app-tauri-migration-design.md`),
with zero rendered-output change. That app is still a plain web frontend — no
native window, no Rust, no `src-tauri/`. This PR wraps it in Tauri v2, proving
the frontend↔Rust IPC bridge with a trivial `ping` command, without yet
building any real recording functionality (that starts in PR 3).

Key PRD constraints this PR must honor (PRD §6.2, §8):
- Use Tauri with a secure Rust backend.
- Use restrictive Tauri capabilities; avoid unnecessary network, shell, or
  filesystem access.

### Decisions made during design

- **Toolchain**: Rust/Cargo (rustup stable 1.98.1) and Tauri v2 CLI
  (`@tauri-apps/cli@2.11.5` via `pnpm dlx`) were already installed and
  verified in PR 1's design phase; Fedora build dependencies
  (`webkit2gtk4.1-devel`, `librsvg2-devel`, `libappindicator-gtk3-devel`,
  `file-devel`, `wget`) were installed via `sudo dnf install` at that time.
  No further toolchain setup needed for this PR.
- **Scaffold approach**: use the official Tauri CLI's `init` command against
  the existing `apps/sound-app` directory, rather than hand-writing
  `Cargo.toml`/`tauri.conf.json`/Rust source from scratch. This generates
  config matching Tauri v2's actual current schema, which is safer than
  manually authoring it. No root-level Cargo workspace is introduced —
  `src-tauri/Cargo.toml` stands alone, since this is the only Rust crate in
  the repo so far.
- **App identifier**: `com.soundrecorder.app` (reverse-DNS style, required
  for OS integration/bundling). The `init` command's CLI version available
  here has no `--identifier` flag, so this gets hand-set in
  `tauri.conf.json` after scaffolding.
- **Icons**: deferred to a later, release-focused PR. Tauri's own
  placeholder icon set (generated by `init`) is sufficient for `tauri dev`;
  real branded icons only matter for `tauri build` bundling, which isn't
  exercised yet.
- **Capabilities posture**: restrictive by omission, not by
  addition-then-lockdown. The generated scaffold typically includes
  `tauri-plugin-opener` (for opening external links) — this gets removed
  from `Cargo.toml` and `capabilities/default.json` since nothing in this
  PR needs it. No shell or HTTP/network plugin is added at all. Custom
  `#[tauri::command]` functions (like `ping`) are not gated by Tauri v2's
  capabilities/permissions system — that system governs *plugin* commands
  (fs, dialog, shell, http, etc.), not app-defined ones — so `ping` needs
  no capability grant, only registration in the invoke handler.
- **Script wiring**: add a `"tauri": "tauri"` pass-through script to
  `apps/sound-app/package.json` (the standard Tauri+pnpm convention), so
  `pnpm --filter sound-app tauri dev`/`tauri build` work. The existing
  `dev`/`build` Turbo tasks are deliberately left as pure Vite web-server
  tasks — the Tauri shell is invoked explicitly via the new `tauri` script,
  not folded into the default `dev` task, so routine web-only iteration
  doesn't unexpectedly pop up a native window.
- **Environment note**: this development machine has a real Wayland
  display (`DISPLAY=:0`, `WAYLAND_DISPLAY=wayland-0`), so `tauri dev` opens
  an actual native window here for manual verification — not a headless
  stub.

## Architecture

### Directory structure (additions)

```
apps/sound-app/
  src-tauri/
    Cargo.toml
    tauri.conf.json          # devUrl -> :1420, frontendDist -> ../dist,
                              # identifier -> com.soundrecorder.app,
                              # beforeDevCommand -> "pnpm dev",
                              # beforeBuildCommand -> "pnpm build"
    capabilities/
      default.json           # pruned: no opener plugin, no shell, no http
    icons/                   # Tauri-generated placeholders
    src/
      main.rs                # entry point, calls lib.rs's run()
      lib.rs                 # app builder, registers the ping command
  package.json                # + "tauri": "tauri" script
  src/
    App.tsx                   # + a small ping-button UI element
    App.test.tsx              # + a mocked-invoke test for the ping button
```

### The ping command

Rust (`src-tauri/src/lib.rs`):
```rust
#[tauri::command]
fn ping() -> String {
    "pong".to_string()
}
```
registered via `tauri::generate_handler![ping]` in the `Builder::default()`
chain. A `#[cfg(test)]` unit test in the same file calls `ping()` directly
and asserts it returns `"pong"` — this is a plain Rust function, no Tauri
runtime context required to test it.

Frontend (`src/App.tsx`): a button labeled "Ping backend" that calls
`invoke("ping")` from `@tauri-apps/api/core` on click and renders the
result string. This is deliberately small and will very likely be replaced
outright when PR 3 adds the real recording UI — it exists only to prove the
IPC bridge, not as a permanent feature.

### Testing strategy

- Rust: `cargo test` (run from `src-tauri/`) covers the `ping` function
  directly.
- Frontend: a Vitest test mocks `@tauri-apps/api/core`'s `invoke` (via
  `vi.mock`) to resolve `"pong"`, clicks the ping button, and asserts the
  result renders — proves the frontend wiring without needing a real Tauri
  runtime under jsdom.
- Manual: `pnpm --filter sound-app tauri dev` opens a real native window on
  this machine's Wayland display. Click the button, confirm "pong" appears,
  close the window. This is the only step that proves the actual
  frontend↔Rust bridge works end-to-end, since the other two tests each
  mock away one side of it.

## Explicitly out of scope for this PR

- Any real audio capture, recording state machine, or file writing (PR 3+).
- Tray/menu-bar controls, window persistence, minimize-to-tray behavior.
- App icons/branding for `tauri build` bundling.
- Changing the default `pnpm dev`/`pnpm build` Turbo tasks to launch the
  desktop shell instead of the web-only Vite server.
- Windows/macOS-specific Tauri configuration (this PR's manual verification
  is Linux-only, matching PR 1's OS-priority decision).

## Deviations from this spec (recorded after implementation)

- This spec's "Capabilities posture" section assumed `tauri-plugin-opener` would be present in the generated scaffold and need removing. In practice, `@tauri-apps/cli@2.11.5`'s `init` command never generates it — there was nothing to prune. `capabilities/default.json` ships with only `"core:default"` from the start.
- Content Security Policy (`tauri.conf.json`'s `"security": { "csp": null }`) was left at the CLI's generated default (no CSP at all) in this PR. This is a real gap against PRD §6.2's "restrictive... avoid unnecessary network access" posture that this spec did not address. **Deferred to PR 3's planning** — setting a proper CSP needs a live `tauri dev` run to confirm it doesn't break Vite's dev-server/HMR origin, which needs to happen as part of implementation work, not retroactively.
